## Findings by checklist
### 1) Open redirect vulnerabilities — Critical
The current redirect chain is not strict enough:
- In the login UI, login-form.tsx passes the `from` query param into the provider buttons.
- In google-button.tsx and github-button.tsx, `redirectTo` is accepted from the caller and then used to derive `next` through:
  - `redirectTo && redirectTo.startsWith("/")`
  - `redirectTo: `${window.location.origin}/auth/callback?next=${encodeURIComponent(safeRedirect)}``
The bug is that `startsWith("/")` is not sufficient. A value like `//evil.com` also starts with `/`, and the callback route later treats that as redirectable. The callback route is [frontend/app/auth/callback/route.ts](frontend/app/auth/callback/route.ts#L4-L16):
- It reads `next` from the query string.
- It defaults to `/dashboard` if nothing is supplied.
- It redirects with:
  - `NextResponse.redirect(`${origin}${next.startsWith("/") ? next : `/${next}`}`)`
That is unsafe because `//evil.com` becomes a protocol-relative external redirect target. The `next` parameter is not canonicalized and not validated against a strict allowlist.
What to fix before production:
- Keep a server-side validation function that accepts only a relative path inside the same origin.
- Reject:
  - any value not starting with `/`
  - any value starting with `//`
  - any absolute URL such as `http://` or `https://`
  - any path not on an approved internal allowlist if you want to be strict.
- In practice, enforce a helper like:
  - `if (!next || !next.startsWith("/") || next.startsWith("//")) { next = "/dashboard"; }`
  - additionally validate with `new URL(next, origin)` and ensure the host is the same origin.

### 3) RLS coverage — Critical / Warning

What to fix before production:

     - `auth.uid() = user_id`
     - or the equivalent ownership logic
- Do not rely on client-side filtering as the authorization boundary.
- Any protected API or page should ask the server to read only rows the current authenticated user is allowed to access.

### 4) Session / middleware coverage — Critical
This is not covered in the repo.
What I found:
- auth.tsx defines `AuthProvider` and only hydrates the user from `supabase.auth.getSession()`. That is not a server trust check.
- It updates user state on auth change, but it does not call `supabase.auth.getUser()` on protected routes.
- The file middleware.ts contains a `updateSession` helper that refreshes the Supabase session through `getUser()`, but that helper is not connected to a Next.js middleware route.
- There is no top-level middleware file in the repo root that matches `/(dashboard|feed|account|admin|...)` and redirects unauthenticated users away.
- The dashboard page at [frontend/app/dashboard/[[...rest]]/page.tsx](frontend/app/dashboard/[[...rest]]/page.tsx#L1-L3) is just a static render and is not protected by a server guard.
What to fix before production:
- Create a real root-level Next.js middleware that runs on protected routes:
  - `matcher: ["/dashboard/:path*", "/account/:path*", "/admin/:path*"]` or equivalent
- In that middleware, call `supabase.auth.getUser()` and redirect any unauthenticated request to `/login`.
- Add server-side protection to page routes or route handlers that call `getUser()` before reading the request or rendering data.
- Keep `getSession()` only as a session-read convenience. It can be stale. Server trust must use `getUser()`.

### 5) Callback route validation — Warning / Critical
The callback route is route.ts.
Current behavior:
- It reads `code` from the query string.
- If `code` exists, it calls `await supabase.auth.exchangeCodeForSession(code)`.
- On success, it redirects to the `next` path, or to `/dashboard` by default.
- On failure, it redirects to `/auth/error`.
That is acceptable for the happy-path/invalid-code error path. However, the string `next` is not properly validated. The callback route is one of the vulnerable surfaces.
What to fix before production:
- Keep the `code` check as is, but make the fallback safe.
- Validate `next` before redirect.
- If `exchangeCodeForSession` fails, redirect to a fixed error page and do not pass a dynamic `next` target.

### 8) Rate limiting — Warning
I do not find any rate-limit or brute-force protection in the frontend.
What I found:
- OAuth is initiated directly from the browser using `supabase.auth.signInWithOAuth()` in the provider buttons.
- No custom throttling, CAPTCHA, token bucket, or request-limit logic exists.
- There is no email/password sign-in implementation here, so credential-stuffing protection for password auth is not relevant in this repo.
- Supabase itself provides some provider-level protection, but that is a dashboard-side feature.
What to fix before production:
- If you add email/password auth, add queueing/throttling, lockout checks, or an abuse detection layer before calling Supabase.
- For OAuth, stack a provider-specific throttle / session challenge to constrain repeated login attempts from the same IP or user.

### 10) Sign-out flow — Warning
The sign-out entry point is in auth.tsx:
- `logout()` calls `await supabase.auth.signOut()`
- Then it clears `currentUser` from React state
The UI sign-out entry point is in Nav.tsx and the navigation buttons call `logout()` before redirecting to `/`.
Current status:
- The browser-side session is cleared through `signOut()`.
- The state is reset in React.
- There is no server-side redirect guard to immediately deny a user access to a protected page after sign-out.
What to fix before production:
- Add a route guard for protected pages that uses `getUser()` on the server and redirects to `/login` if the session is missing or invalid.
- After `signOut()`, call a server-side reset if you use route handlers or route protection that might still trust server cookies.
- Protect the dashboard and any account/admin route from direct render and API access.
